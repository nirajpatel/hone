## Step 4 — Edit proposals (1:1 against findings)

Each proposal maps to one observed failure mode. If a mode has zero occurrences, no edit is added. Bloat budget: net token delta of the prompt versus today; must be ≤0 unless explicitly justified.

### F1 — followedNoChange (13 occurrences, dominant) + repeatedGuidance (8) + ignoredHighConfidence (8)

These three are the same underlying loop: the model proposes a tiny grind move (e.g. "Grind finer by 0.2–0.3"), the user follows it, nothing changes, and the model proposes the same direction again with a similarly tiny step the next brew. Three brews in (Willy's Beans Lychee, Mazateca Mujeres, Banko Taratu show this clearly), the user starts ignoring the suggestion. Same root cause for all three modes.

**Root cause in current prompt** ([supabase/functions/make-server-23508aac/index.ts](supabase/functions/make-server-23508aac/index.ts)):
- Line 2410 / 2789: *"Prefer the smallest reasonable change that could plausibly fix the issue. Avoid large jumps unless history clearly shows they are necessary."*
- Line 2419 / 2798: *"Use 'High' only when supported by at least two prior brews or a direct comparison."*
- Line 2398 / 2776: *"Avoid Repetition: ... If a previous brew tried a parameter change and it didn't improve things, suggest a different approach."* — too soft; the model never actually flags whether the previous suggestion was followed.

The minimum-change rule overrides the soft repetition rule because the model has no machinery to *count* how many small steps in this direction it has already proposed. The user's data has cases like Willy's Beans where "Grind finer by 0.2–0.3 from 5.0 to ~4.7–4.8" is recommended on 4 separate brews verbatim.

**Proposed edit (single change to both prompts):** replace the soft "Avoid Repetition" bullet with an explicit escalation rule:

> When the same parameter+direction has been suggested in any of the three prior brews on this coffee, you MUST NOT repeat the same magnitude. Either (a) escalate the magnitude meaningfully (≈2× the prior step) and explain why, (b) switch to a different parameter from the decision hierarchy, or (c) explicitly recommend holding all parameters and re-tasting to confirm the diagnosis. The minimal-change preference does not apply once a small step has already been tried without improvement.

This carries one new clause but also kills two existing rules that overlap with it ("Avoid Repetition" bullet + the redundant "Prefer minimal changes" tail of rule A). Net length: roughly neutral.

**Bloat budget**: net 0 (replaces ~3 lines, adds ~3 lines).

### F2 — followedButRegressed (7 occurrences)

High-confidence suggestions caused quality drops (e.g. "Grind coarser by 0.5–1.0" → Decent → Bad on Arboretum and Frame; "Increase final weight by 10–15g" → Excellent → Decent on Banko Taratu). The model overclaims High when it shouldn't.

**Root cause in current prompt**: rule C says *"Use 'High' only when supported by at least two prior brews or a direct comparison"* but doesn't penalize a recent regression. Line 2419 / 2798.

**Proposed edit**: tighten rule C's High criterion with one extra clause:

> Downgrade confidence to Medium or Low whenever the most recent brew that followed a similar suggestion regressed in quality, or whenever the suggested direction would push past a known-good baseline value (e.g. a previous excellent brew used a coarser grind than what you're proposing).

**Bloat budget**: +1 line (~25 tokens). Justified because regressions are the worst observed outcome — they directly cause bad cups.

### F3 — staleDiagnosis (2 occurrences)

Both on Mazateca Mujeres: `primaryIssue` stayed *"under-extracted due to fast flow"* across three brews even though grindSetting, brewTime, and finalWeight all changed and brewTime grew from 175s to 220s. Diagnosis didn't update with the data.

**Root cause in current prompt**: the prompt asks for *one* primary failure mode (rule D, line 2422 / 2801) but never tells the model to re-derive it when prior parameters have moved. The diagnosis sticks.

**Proposed edit**: append one clause to rule D:

> Re-derive the primary failure mode from the baseline brew's recorded outcome alone; do not carry forward the diagnosis from any prior brew. If the same diagnosis recurs across consecutive brews despite parameter changes, treat that as evidence that the diagnosis itself is wrong and consider an alternative cause (e.g. dose / ratio rather than grind, or puck preparation).

**Bloat budget**: +2 lines (~40 tokens). Justified by the loop pattern in the data — sticky diagnosis is what feeds F1.
